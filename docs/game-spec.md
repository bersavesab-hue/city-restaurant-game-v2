# 餐饮经营 v2 — 首发范围规范

## 产品方向
首发版本采用“单店从小到大升级”的经营模式。玩家围绕一家餐厅持续经营、优化和扩建，不以总部和多店管理作为首发主循环。

仓库中已有比首发范围更丰富的底层系统。只要稳定且不妨碍首发流程，可以保留作为底层能力；不因为首发 UI 暂不展示就直接删除。

## 核心循环
采购原料 → 库存与损耗 → 菜单/菜品生产 → 顾客需求与服务能力 → 成交与评价 → 收入/成本结算 → 门店成长与升级。

一个功能只有在“状态读取 → 用户操作 → 业务处理 → 状态变化 → UI 反馈 → 保存恢复”全部贯通后，才算完成。

## 首发重点
- 单一活跃门店。
- 采购、库存、菜品、员工、营业、结算和升级形成完整闭环。
- 经营反馈至少覆盖：营业额、净利润、客流、星级/评价、缺货或服务瓶颈。
- 装修首发优先采用固定位置或阶段升级，不把自由摆放作为首发硬依赖。
- 活动和事件必须有明确收益、成本或风险，不只改变文字。
- 玩家在不看广告的情况下也必须存在可持续经营路线。

## 内容预算
以下是首发内容预算方向，不是删除仓库现有内容的命令：
- 菜品：先保证约 12–18 个可用且差异明确的菜品。
- 原料：先保证约 6–10 个核心原料类别可形成采购与缺货决策。
- 员工：首发优先厨师、服务、清洁等核心岗位，共用员工管理框架。
- 活动：先保证约 3–4 种有实际效果的活动。
- 经营事件：先保证约 15–20 条真正影响经营的事件。
- 成长：先形成 3 个清晰的门店成长阶段。

## 首发暂缓
- 总部层。
- 多店同时经营。
- 联网排名。
- 依赖付费 AI API 的实时玩法。
- 为表现效果而引入复杂人物实时寻路。
- 复杂金融系统作为首发核心操作。

## 已有底层能力的处理
当前仓库已有顾客、菜品、采购、库存、员工、租赁、市场、装修、会员、评价、营业模拟等大量系统。首发重构优先“收窄 UI 暴露面”，而不是先删除底层。

## 时间与离线
当前代码已有暂停、1x/2x/4x 和模拟推进能力，但“现实时间与游戏时间映射、后台恢复、离线收益”仍需单独冻结规则后再实现。首发不得自行假设离线收益。

## 验收定义
首发最小可玩闭环至少要能证明：
1. 玩家有初始资金；
2. 采购会正确扣款并增加库存；
3. 菜品受配方和库存约束；
4. 营业会产生真实订单；
5. 订单受服务/生产能力限制；
6. 成交产生收入并消耗库存；
7. 工资、租金等成本按既定规则结算；
8. 玩家能通过经营完成至少一次门店成长；
9. 退出并重新进入后关键状态仍可恢复。
