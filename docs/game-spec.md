# 餐饮经营 v2 — 首发范围规范

## 产品方向
首发版本采用“单店从小到大升级”的经营模式。玩家围绕一家餐厅持续经营、优化和扩建，不以总部和多店管理作为首发主循环。

仓库中已有比首发范围更丰富的底层系统。只要稳定且不妨碍首发流程，可以保留作为底层能力；不因为首发 UI 暂不展示就直接删除。

## 核心循环
采购原料 → 库存与损耗 → 菜单/菜品生产 → 顾客需求与服务能力 → 成交与评价 → 收入/成本结算 → 门店成长与升级。

一个功能只有在“状态读取 → 用户操作 → 业务处理 → 状态变化 → UI 反馈 → 保存恢复”全部贯通后，才算完成。

## 首发重点
- 单一活跃门店。
- 采购、库存、菜品、员工、营业、结算和升级形成完整闭环。
- 经营反馈至少覆盖：营业额、净利润、客流、星级/评价、缺货或服务瓶颈。
- 装修首发优先采用固定位置或阶段升级，不把自由摆放作为首发硬依赖。
- 活动和事件必须有明确收益、成本或风险，不只改变文字。
- 玩家在不看广告的情况下也必须存在可持续经营路线。

## 内容预算
以下是首发内容预算方向，不是删除仓库现有内容的命令：
- 菜品：先保证约 12–18 个可用且差异明确的菜品。
- 原料：先保证约 6–10 个核心原料类别可形成采购与缺货决策。
- 员工：首发优先厨师、服务、清洁等核心岗位，共用员工管理框架。
- 活动：先保证约 3–4 种有实际效果的活动。
- 经营事件：先保证约 15–20 条真正影响经营的事件。
- 成长：先形成 3 个清晰的门店成长阶段。

## 首发暂缓
- 总部层。
- 多店同时经营。
- 联网排名。
- 依赖付费 AI API 的实时玩法。
- 为表现效果而引入复杂人物实时寻路。
- 复杂金融系统作为首发核心操作。

## 已有底层能力的处理
当前仓库已有顾客、菜品、采购、库存、员工、租赁、市场、装修、会员、评价、营业模拟等大量系统。首发重构优先“收窄 UI 暴露面”，而不是先删除底层。

## 时间、后台与存档
首发时间规则固定为：
- 1×：每现实 1 秒推进 2 个游戏分钟。
- 2×/4×：在 1× 基础上成比例加速。
- 普通经营页面、菜品页、员工页和库存页切换不自动暂停；只有明确的暂停操作改变 `runtime.paused`。
- 新档首次启动自动进入运行状态。
- 读取已有存档时保留玩家上次的暂停状态和速度。
- 切到后台或页面隐藏时立即存档并停止实时计时器。
- 回到前台时重启实时计时器，但不补算后台经过的现实时间。
- 首发关闭离线收益；后续若加入，必须单独设计时长上限、产能和资源约束。

首发自动存档规则固定为：
- 默认使用 `auto` 槽。
- 前台运行时每 30 秒自动保存。
- 切后台/pagehide 时立即保存。
- 每次新存档写入前，上一份结构有效的主存档保留为滚动备份。
- 主存档损坏时可自动尝试滚动备份；未来版本存档禁止用旧备份静默降级。
- 主档和备份都无法读取时，进入禁止自动覆盖状态，等待后续 UI 给出恢复/新开档选择。

## 验收定义
首发最小可玩闭环至少要能证明：
1. 玩家有初始资金；
2. 采购会正确扣款并增加库存；
3. 菜品受配方和库存约束；
4. 营业会产生真实订单；
5. 订单受服务/生产能力限制；
6. 成交产生收入并消耗库存；
7. 工资、租金等成本按既定规则结算；
8. 玩家能通过经营完成至少一次门店成长；
9. 退出并重新进入后关键状态仍可恢复。
